# Рисунок 8 — Схема ролей и функций веб-приложения VisKet (UML Use Case Diagram)

## Словесное описание схемы

Диаграмма вариантов использования (UML Use Case Diagram) иллюстрирует функциональные требования платформы VisKet, распределённые между тремя акторами: **Гость**, **Резидент** (заказчик/исполнитель) и **Администратор**. Диаграмма отображает отношения обобщения (generalization), включения (<<include>>) и расширения (<<extend>>) между вариантами использования.

---

## Актёры системы

```
┌─────────────────────┐
│       Гость         │  ← Базовый актёр (неавторизованный пользователь)
└────────┬────────────┘
         │ ▲
         │ │ (generalization)
┌────────┴────────────┐
│     Резидент        │  ← Наследует все функции Гостя
│ (заказчик/          │     Может быть как заказчиком, так и исполнителем
│  исполнитель)       │
└─────────────────────┘

┌─────────────────────┐
│   Администратор     │  ← Отдельный актёр с привилегированным доступом
└─────────────────────┘
```

## Варианты использования (Use Cases)

### 1. Актёр «Гость»

Гость — неавторизованный пользователь платформы. Имеет доступ только к просмотру публичного контента и регистрации.

| ID | Вариант использования | Описание |
|----|----------------------|----------|
| UC-1 | Просмотреть главную страницу | Просмотр ленты постов и вакансий с фильтрацией |
| UC-2 | Просмотреть профиль пользователя | Просмотр публичной информации любого пользователя |
| UC-3 | Зарегистрироваться | Создание учётной записи (email, пароль, аватар, биография, навыки) |
| UC-4 | Авторизоваться | Вход в систему по email/паролю |

**Отношения:**

```
UC-4 Авторизоваться
  ├── <<extend>> ── UC-4a Авторизоваться через Google
  └── <<extend>> ── UC-4b Авторизоваться через GitHub
```

(Варианты UC-4a и UC-4b расширяют UC-4, предоставляя альтернативные способы аутентификации через OAuth-провайдеров.)

### 2. Актёр «Резидент»

Резидент — авторизованный пользователь, наследующий все возможности Гостя (отношение generalization). Может выступать как в роли заказчика (создание вакансий, найм), так и в роли исполнителя (отклик на вакансии, выполнение заказов).

| UC-5 | Создать пост/вакансию | Публикация контента с возможностью прикрепить вакансию |

## Полная структура отношений

### Легенда

| Обозначение | Значение |
|-------------|----------|
| ───▶ | Ассоциация (актёр взаимодействует с вариантом использования) |
| ──▶ (стрелка с пустым треугольником) | Обобщение (generalization) — дочерний актёр наследует функции родительского |
| <<include>> ──▶ | Включение — базовый вариант использования обязательно включает указанный |
| <<extend>> ──▶ | Расширение — базовый вариант использования может быть расширен указанным при выполнении условия |

### Стилистические рекомендации

- **Актёры:** фигурки-стики (stick figures) слева, соединённые линиями с вариантами использования.
- **Варианты использования:** овалы/эллипсы с текстом внутри, сгруппированные в блоки по акторам.
- **Границы системы:** прямоугольник с надписью «VisKet» — граница системы.
- **Отношения:**
  - Сплошная линия — ассоциация (актёр ↔ вариант использования).
  - Стрелка с пустым треугольником (─▷) — обобщение (от Резидента к Гостю).
  - Пунктирная стрелка со стереотипом `<<include>>` — отношение включения.
  - Пунктирная стрелка со стереотипом `<<extend>>` — отношение расширения.
- **Цвета:**
  - Синий (#3B82F6) — зона Гостя.
  - Зелёный (#22C55E) — зона Резидента.
  - Фиолетовый (#8B5CF6) — зона Администратора.
  - Серый (#9CA3AF) — граница системы.
- **Шрифт:** Times New Roman 12 пт для подписей, 10 пт для текста внутри фигур.
- **Фон:** белый, без сетки.

## Примечание для вставки в курсовую

> Рисунок 8 демонстрирует распределение функциональных ролей и вариантов использования веб-платформы VisKet. Система предусматривает три уровня доступа: **Гость** (неавторизованный пользователь с ограниченным просмотром), **Резидент** (авторизованный пользователь, совмещающий роли заказчика и исполнителя) и **Администратор** (модератор с привилегиями управления пользователями, контентом и спорами). Отношения обобщения, включения (<<include>>) и расширения (<<extend>>) отражают иерархию функциональности и зависимости между вариантами использования. Ключевой особенностью архитектуры является единая роль резидента, который может как создавать вакансии (заказчик), так и откликаться на них (исполнитель), что обеспечивает гибкость взаимодействия на платформе.
